PART 1
Product Requirements Document (PRD)
1.1 Executive Summary
The AI Customer Support Chatbot Builder is a self-serve SaaS product that lets any small business turn its existing
FAQ content into a working, embeddable AI chat widget in minutes, with no coding and no developer involvement.
A business owner pastes their FAQ text, the system automatically chunks and embeds that content, and visitors to
the business's website can immediately start asking questions that are answered using only that business's own
content — never invented information.
The defining constraint of this build is cost: the entire MVP runs on free-tier infrastructure. HuggingFace
sentence-transformers provide embeddings at zero cost, Groq supplies fast, free Llama 3 inference, and Supabase
provides both the relational database and the vector store (via pgvector) in a single free Postgres instance. This
means the product can be built, launched, and operated for real businesses before a single rupee of infrastructure
spend is required — payment processing via Razorpay is only introduced once the product needs to convert free
users into paying ones.
1.2 Problem Statement
Small businesses cannot realistically staff round-the-clock live chat support. Customers expect instant answers to
repetitive questions (return policy, pricing, hours, shipping, how something works) at any hour, but hiring even a
part-time support agent is not viable for most small operations. Existing chatbot platforms solve this in theory, but in
practice they are priced for mid-size and enterprise teams ($20–$100+/month) and frequently require technical
setup (API keys, webhook configuration, custom integrations) that a non-technical small business owner cannot
complete alone.
This product closes that gap with a self-serve flow built entirely on free AI infrastructure: paste your FAQ in, copy a
script tag out, and the website has a 24/7 support assistant that only ever answers from the business's own
content.

1.6 User Flow — Business Owner
1. Owner visits the platform and signs up using email, handled by Supabase Auth.
2. Lands on the dashboard; sees a prompt to “Create your first bot” if no bots exist yet.
3. Clicks “Create Bot” and gives it a name (for example, “Support Bot”).
4. Is taken to the bot’s detail page, where they paste FAQ text into a textarea (or, post-MVP, upload a .txt file).
5. Clicks “Train Bot” and sees a loading state while the backend chunks, embeds, and stores the content.
Edge case: if the pasted text is empty or below a minimum length, the UI blocks submission with an inline
message.
6. Once complete, sees a success message along with the embed snippet (a script tag containing a unique
widget key) and a “Copy” button.
7. Pastes that snippet into their own website’s HTML, typically just before the closing </body> tag.
8. Can return at any time to view query logs, re-upload or retrain the FAQ (with a confirmation step, since
retraining deletes and replaces all existing chunks for that bot), create additional bots if their plan allows, or
upgrade their plan when they hit a limit.
1.7 User Flow — End Website Visitor
1. Visitor lands on the business’s website (for example, an online store).
2. Sees a floating chat bubble in the corner of the screen — the widget.
3. Clicks it, and a small chat panel opens.
4. Types a question (for example, “What’s your return policy?”).
5. The question is sent to the backend behind the scenes, identified only by the bot’s public widget key.
6. The backend finds the most relevant FAQ chunks and sends them, along with the question, to Groq.
7. Groq’s generated answer is returned and displayed in the chat panel within a couple of seconds.
8. The visitor can continue asking follow-up questions in the same session.
9. If the bot has no relevant information for a question, it says so honestly rather than inventing an answer.
Edge case: if the backend or an upstream AI service is temporarily unavailable, the widget shows a friendly “try
again in a moment” message instead of failing silently.

1.10 Competitive Landscape
Established players such as Intercom Fin, Tidio, Chatbase, and Crisp offer comparable FAQ-bot functionality but
are priced for funded teams, typically starting in the $20–$100+/month range with usage-based add-ons. This
product’s differentiation is structural, not feature-based: by building the entire MVP on free-tier AI and database
infrastructure, it can offer a genuinely free starting tier to small businesses that the competition cannot match
without subsidizing losses.
1.11 Assumptions and Constraints
• Groq and HuggingFace free-tier rate limits may require a paid upgrade path once usage scales beyond a few
thousand queries per day.
• MVP supports text-pasted FAQ content only; file parsing is post-MVP.
• MVP is English-language only; multilingual support is a future feature.
• Each business is assumed to have basic ability to paste a script tag into their website HTML, or use a page
builder that supports custom scripts.

Performance
• End-to-end visitor query response time (question sent → answer displayed) should stay under 3 seconds
under normal load, relying on Groq’s low-latency inference.
• Embedding generation for a typical FAQ upload (under ~5,000 words) should complete within a few seconds
during training.
Scalability
• The FastAPI backend should be stateless so additional instances can be added behind the hosting provider’s
load balancing without code changes.
• Vector search via pgvector should remain performant as chunk volume grows by using an appropriate index
(see Part 4, Section 4.3).
Availability
• The product should clearly communicate degraded states (e.g. “temporarily unavailable”) rather than fail
silently, especially given free-tier hosting cold-start behavior (see Part 3, Section 3.6).
Usability
• A non-technical business owner should be able to go from signup to a working embeddable widget without
reading documentation, in under 5 minutes.
Maintainability
• Chunking, embedding, retrieval, and answer-generation logic should be implemented as separable functions
within FastAPI so any one AI provider (HuggingFace, Groq) can be swapped later without rewriting the pipeline
structure.
2.4 Security Requirements
• Authentication shall use Supabase Auth with JWT-based session tokens; the dashboard and management
API routes require a valid JWT.
• Each bot’s public widget key shall be a long, random, non-guessable token used only to scope a visitor’s chat
session to that bot — it shall never grant access to dashboard data, logs, or other bots.
• The public chat endpoint shall be rate-limited per widget key and per IP address to prevent abuse and to
protect free-tier Groq/HuggingFace quotas.
• All visitor input shall be treated as untrusted: sanitized before storage and before being placed into the LLM
prompt, to reduce prompt-injection risk that could otherwise be used to make the bot reveal other bots’ content
or ignore the “only answer from FAQ content” instruction.
• Data shall be encrypted in transit via HTTPS/TLS on all endpoints, and at rest via Supabase’s default
Postgres encryption.
• Provider API keys (HuggingFace, Groq, Razorpay) shall be stored only as backend environment variables
and shall never be exposed to the dashboard frontend or the widget JavaScript.
• CORS shall be configured narrowly: dashboard/management API routes accept requests only from the
product’s own frontend origin, while the public widget chat route deliberately allows cross-origin requests, since
it must be callable from any business’s website domain.

Two distinct data flows run through the same FastAPI backend: the ingestion flow, which is owner-triggered and
happens rarely (only on upload or retrain), and the query flow, which is visitor-triggered and happens constantly.

uses all three AI components together.

• If the Groq API call fails or times out, the backend returns a graceful “temporarily unavailable, please try
again” response rather than an error the widget cannot handle.
• If vector search returns no chunk above the similarity threshold, the backend short-circuits to the standard “I
don’t know” response without calling Groq at all, saving a paid/rate-limited call.
• All backend exceptions are logged server-side; the widget only ever sees a small, well-defined set of
response states (answer, fallback, temporary error).
3.8 Recommended Build Order
1. Prove the core AI loop works standalone — chunk, embed, store, retrieve, and get a Groq answer — before
building any user interface.
2. Wrap that working loop in FastAPI endpoints.
3. Build and test the widget JS against those endpoints using a blank test page.
4. Build the Next.js dashboard: authentication, FAQ upload, embed snippet display, and logs.
5. Add multi-bot support and plan limit enforcement.
6. Add Razorpay integration and deploy publicly.
This order front-loads the riskiest, least familiar part of the project — AI retrieval quality — so problems surface in
week one rather than after the entire interface has already been built around it. Dashboards and authentication are
mechanical, lower-risk work that can be done with confidence once the core loop is proven.

4.1 Entity Relationship Overview
All persistent data lives in a single Supabase Postgres instance, with the pgvector extension enabled for
embedding storage and similarity search. The core relationships are:
• One business can own many bots (1—N).
• One bot can have many documents (FAQ chunks) (1—N).
• One bot can have many queries_log entries (1—N).
• Deleting a bot should cascade-delete its documents and query logs, since orphaned chunks/logs serve no
purpose.

4.4 Data Retention Considerations
• Retraining a bot deletes all of its existing documents rows before inserting the newly submitted chunks, per
FR-13.
• Deleting a bot cascades to remove its documents and queries_log rows, preventing orphaned data.
• queries_log can grow indefinitely under normal use; a future archival or rolling-retention policy (e.g. keep the
last 90 days in the hot table) should be considered once usage scales, to stay within the Supabase free-tier
storage cap.
4.5 Sizing Estimate on the Free Tier
Each all-MiniLM-L6-v2 embedding is 384 float values (~1.5KB uncompressed). With Supabase’s ~500MB free
Postgres allowance shared across all relational data, a rough back-of-envelope budget of 300MB dedicated to
embeddings allows on the order of 150,000–200,000 FAQ chunks across all businesses before storage becomes a
concern — comfortably enough headroom for the MVP and early post-launch period, with the remaining allowance
covering business, bot, and log rows.
